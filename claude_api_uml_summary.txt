Goal

Prepare backend-first architecture for pilgrimage route handling.
Mobile app should be thinner.
All pilgrimage data should be stored and fetched through RTK Query by default.
Schedule shown in mobile should be simplified.
Server should calculate route state, distance, active schedule item, and fallback logic.


Current Direction

Administrator will prepare a JSON config on the server side like:

{
  "day1": "https://www.google.pl/maps/dir/....",
  "day2": "https://www.google.pl/maps/dir/...."
}

This continues up to day14.

These Google Maps URLs are source input only.
Server should transform them into normalized route data for the app.


Important Architectural Rule

Do not rely on raw Google Maps URLs as final app data.
Treat them as import source.
Server should parse, normalize, enrich, and store its own structured model.


Target Responsibilities

Administrator:
- provides source JSON with Google Maps URLs per day
- optionally reviews parsed route draft

Server:
- imports route source config
- parses Google Maps URL
- extracts stops, waypoint order, coordinates where possible
- optionally calls routing/geocoding service
- computes distances between points
- computes total day distance
- creates simplified schedule
- stores normalized pilgrimage route data
- computes current route state from GPS and time
- returns ready DTOs for mobile

Mobile app:
- sends current GPS location and timestamp
- fetches normalized pilgrimage/day data via RTK Query
- fetches computed route state via API
- renders UI only
- should not parse Google Maps URLs
- should not compute route matching logic locally


Main Business Rules

1. All pilgrimage data should be delivered through RTK Query by default.
2. Default schedule in mobile should be simplified.
3. Server should compute:
- active schedule item
- current town / nearest route point
- traveled distance
- remaining distance
- source of calculation: gps or time-estimated
- label for UI, for example "W okolicy" or "Wg harmonogramu"
4. If GPS is unavailable, server should fallback to schedule/time logic.
5. Mobile should receive precomputed route state instead of reproducing business rules locally.

- basic pilgrimage metadata
- day list

- day details

- simplified schedule only

- time-based fallback state

RTK Query cache should store:
- pilgrimage metadata
- day details
- simplified schedules
- current route state

RTK Query should be treated as the default client-side source of truth for fetched pilgrimage data.
